## 关键问题定位与修复

- 活体帧编码失败导致永远 frames=0：
  - 现象：`活体帧编码异常 ... name 'base64' is not defined`，随后 `活体检测帧不足`，必然阻止开锁。
  - 修复：设备端补齐 `import base64`，并增加编码异常限频日志，便于后续定位。
- 设备端未实现云端活体调用：
  - 现象：`CloudCommunication' object has no attribute 'check_liveness'`，主循环异常导致后续逻辑不执行。
  - 修复：同步更新 `src/sync/cloud_communication.py`，补齐 `check_liveness()`，并保证设备鉴权头一致。
- 云端复核可用性验证：
  - 在云端完成 DashScope API Key 配置与冒烟测试（`/chat/completions` 返回 200），确认通义千问可用。
- 误报警/预警计时异常：
  - 现象：在成员放行/开锁后仍可能出现预警触发。
  - 修复：在成员识别成功、无人脸、以及陌生访客消失后主动停止预警监控，避免计时残留。

## 活体策略与实现要点（本日迭代）

- 云端策略（组合复核）：
  - provider=qwen 时：先做启发式统计，随后调用通义千问复核；并返回包含 `provider/reason/frame_count` 的结果用于排障。
  - 提示词收紧为“保守判定”，要求关注眨眼/眼睑/嘴唇/微表情/三维光影变化，降低照片误判为真人的概率。
- 设备端策略（取帧与可观测）：
  - 强制输出取帧日志：`活体检测取帧：frames=5/5 unique=...`，用于确认是否真的收集到 5 帧以及帧差异。
  - 增加 burst 取帧：活体判定不再只依赖历史 buffer，而是按 face_box 连续抓拍并裁剪出 5 帧，提升“同一次判断”的帧时间跨度。
- 设备端策略（B 方案：两次投票）：
  - 同一次识别最多进行两次活体复核，间隔 `LIVENESS_RETRY_GAP_SEC`；
  - 若任意一次达到阈值则放行；分数很高（strict）则直接放行；降低真人“偶发未捕捉到动作”导致的一次性误拒。

## 今日使用的关键配置（设备端 .env.pi）

- `LIVENESS_PROVIDER=qwen`（云端）
- `LIVENESS_FRAME_COUNT=5`
- `LIVENESS_MIN_FRAMES=5`
- `LIVENESS_CAPTURE_INTERVAL_SEC=0.35`（拉长 5 帧覆盖窗口，提高捕捉微动作概率）
- `RECOGNITION_INTERVAL_SEC=1.0`（降低频繁触发带来的刷屏与误触发）
- `LIVENESS_RETRY_COUNT=2`
- `LIVENESS_RETRY_GAP_SEC=0.6`
- `LIVENESS_PASS_SCORE_STRICT=0.75`
